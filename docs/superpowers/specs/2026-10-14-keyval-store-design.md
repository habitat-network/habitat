# Generic namespaced keyval store (`internal/keyval`) — design

Status: approved in conversation 2026-10-14, pending written-spec review.

## Goal

One shared, GORM-backed key/value store with expiry and per-consumer
namespaces, so short-lived server-side state stops needing its own table per
feature. Consumers depend on a narrow `Put`/`Get` interface; each is handed a
namespaced instance so keys cannot collide across features.

Two features move onto it in this change:

- `o_auth_requests` (oauthserver) — pushed authorization requests, in-flight
  requests bridging the PDS redirect, and issued authorization codes.
- Login provider flow state — currently serialized into the OAuth session
  cookie.

Expiry is reclaimed by the database on Postgres (a trigger) and at startup on
SQLite.

### Context and constraints

- **Location:** `internal/keyval`, following `internal/db` conventions.
- **Dialects:** `internal/db` already abstracts Postgres and SQLite and
  exposes `db.DialectOf(db)`. `pear` runs Postgres in production
  (`HABITAT_PGURL`) and SQLite otherwise; `sap` and `cmd/home` use SQLite.
- **Schema ownership:** `pear` owns its schema through goose SQL migrations in
  `cmd/pear/migrations/{postgres,sqlite}`, generated by Atlas from each store's
  `Models()` and gated in CI by `moon run pear:migration-check`.
- **TTL is mandatory.** Every entry expires. The store is for temporary state
  only; durable credentials (PDS credentials, registered MCP clients, password
  hashes) must keep their own tables. A registered OAuth `client_id` is a
  credential — expiring one breaks the client — so `registered_clients` stays
  as it is.
- **Go 1.26**, table-per-concern GORM stores, `utils.Opt` constructor options,
  `fmt.Errorf` wrapping, exported `Err*` sentinels — per
  `.claude/rules/go-conventions.md`.

### Success criteria

- A consumer depends on `KV` and is constructed with a namespace; it cannot
  read, overwrite, or delete another consumer's rows.
- Expired entries read as missing, on both dialects, regardless of whether any
  cleanup has run. Correctness never depends on GC.
- On Postgres, expired rows are physically deleted without a Go goroutine.
- On SQLite, expired rows are deleted at startup.
- `moon run pear:migration-check` passes.
- Existing oauthserver and login tests pass, migrated to the new signatures.

### Out of scope

- Migrating any other table. `o_auth_sessions`, `client_auth_requests`,
  `instance_invites`, `spent_tokens`, `registrations` and `invite_rows` keep
  their current storage; they are candidates for later changes, not this one.
- Encryption or compression of values. Values are JSON, stored as-is.
- Listing, scanning, counting, or prefix-scanning keys. A keyval store with
  only `Put`/`Get`/`Delete`/`Consume` cannot be misused into a real query layer.
- Cross-process coordination or a no-expiry mode.

## Architecture

### Data model

One table, `key_values`, in a new `internal/keyval`:

```go
type entry struct {
    Namespace string    `gorm:"column:namespace;primaryKey;size:255"`
    Key       string    `gorm:"column:key;primaryKey;size:255"`
    Value     []byte    `gorm:"column:value;not null"`
    ExpiresAt time.Time `gorm:"column:expires_at;not null;index"`
}

func (entry) TableName() string { return "key_values" }
```

`TableName` is explicit so the name is stable rather than inferred from the Go
identifier. One consequence: an explicit `TableName` **bypasses** GORM's
`NamingStrategy.TablePrefix`, so this table would not pick up `sap`'s `sap_`
prefix. That is the same documented exception `pkg/oauthclient` already has —
its `client_sessions` and `client_auth_requests` are likewise unprefixed, which
is why that package needs `WithTableNames` to retarget. `sap` is not a consumer
in this change; if it becomes one, it needs an equivalent option.

`(namespace, key)` is the primary key, so a `Put` is an upsert via
`clause.OnConflict{Columns: [namespace, key], DoUpdates: [value, expires_at]}`
— the pattern `internal/notify/store.go` and `internal/org/store.go` already
use. `expires_at` is indexed because it is the only other column ever
filtered on.

### Interface

```go
// KV is the narrow store surface a consumer that only writes and reads its
// own state depends on.
type KV interface {
    Put(ctx context.Context, key string, value any, ttl time.Duration) error
    Get(ctx context.Context, key string, dst any) error
}

// Store adds the operations that remove state, plus the ability to derive a
// namespaced child.
type Store interface {
    KV
    Delete(ctx context.Context, key string) error
    Consume(ctx context.Context, key string, dst any) error
    Namespace(ns string) Store
}
```

`Put` marshals `value` as JSON. `Get` and `Consume` unmarshal into `dst`,
which must be a non-nil pointer. JSON keeps the store generic over value shape
while giving each consumer typed reads without hand-rolling a wrapper on both
sides of every call.

`ttl` is a required parameter, not an option, so `expires_at` is never null
and there is no "forever" path that would quietly defeat the trigger.

### Namespacing

```go
func New(ctx context.Context, db *gorm.DB) (Store, error)   // root
```

`New` returns the root, which exists only to be namespaced; no consumer is
handed the root. `Namespace(ns)` returns a new instance bound to that
namespace. Every query the store issues is scoped `WHERE namespace = ?`.

Because the namespace is part of the primary key and present in every
statement, isolation is structural rather than a convention a caller has to
remember: a consumer cannot address another namespace's rows even by passing a
foreign key.

### Expiry semantics

`Get`, `Consume` and `Delete` all filter `expires_at > now()`. A row that has
expired is indistinguishable from a row that was never written: both return
`ErrNotFound`.

This is the load-bearing decision of the design. Expired-row filtering in the
read path already exists in this codebase — `GetPARSession` filters
`expires_at > ?` — and it means a missed, failed, or never-run cleanup pass
costs disk space and nothing else. Cleanup is an optimization; correctness does
not depend on it.

`Consume` is a single atomic statement rather than a read followed by a
delete, because single-use values must not be redeemable twice under
concurrent callbacks:

```sql
DELETE FROM key_values
WHERE namespace = ? AND key = ? AND expires_at > ?
RETURNING value
```

Both dialects support `RETURNING` (SQLite 3.35+, Postgres). `RowsAffected == 0`
is `ErrNotFound`.

`now()` is bound from Go rather than evaluated by the database, so both
dialects agree on the cutoff; SQLite has no `now()`. Clocks are assumed
roughly synchronized between app and database.

### Reclaiming expired rows

**Postgres.** A statement-level trigger fires on writes to `key_values` and
deletes whatever has already expired:

```sql
CREATE OR REPLACE FUNCTION keyval_sweep_expired() RETURNS trigger AS $$
BEGIN
    IF pg_try_advisory_xact_lock(hashtext('keyval.sweep')) THEN
        DELETE FROM key_values WHERE expires_at <= now();
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER keyval_sweep_expired_trg
AFTER INSERT OR UPDATE ON key_values
FOR EACH STATEMENT EXECUTE FUNCTION keyval_sweep_expired();
```

`FOR EACH STATEMENT` rather than `FOR EACH ROW`, so a bulk insert sweeps once
instead of once per row. The `AFTER INSERT OR UPDATE` clause is what keeps it
from recursing: the trigger's own `DELETE` does not re-fire it.

`pg_try_advisory_xact_lock` throttles the sweep. Concurrent writers do not
block each other — the losers simply skip, and the lock is released at commit.

The trigger is `AFTER INSERT OR UPDATE` and nothing else, which is the
accepted limitation: **if writes to the table stop, expired rows stop being
deleted.** The table keeps the same rows it had when writes stopped, and they
remain invisible to readers. A follow-up could reinstate the in-process
sweeper (`internal/oauthserver/gc.go` is the existing pattern) as a backstop;
this change does not.

**SQLite.** No triggers, so `New` runs
`DELETE FROM key_values WHERE expires_at <= ?` once, with the cutoff bound from
Go. This is a dev/test path where the database is a single file whose lifetime
matches the process, so a startup sweep is sufficient; the read-path filter is
what keeps correctness intact either way.

### Schema provisioning

`keyval.Models()` joins `cmd/pear/migrations.Models()`, and the table is
created by Atlas:

```sh
moon run pear:migration-diff -- add_key_values
```

Atlas cannot generate a trigger from a GORM model, so the trigger is a
hand-written follow-up SQL migration in `migrations/postgres`, then
`moon run pear:migration-hash`.

Verified before committing to this approach (Atlas v1.3.0): `migration-check`'s
`atlas schema diff` between the migrations directory and the dumped model DDL
**ignores triggers**, so a hand-written trigger migration produces no drift.
A positive control — adding a column to the dumped DDL — was correctly
reported as drift, confirming the check was live and the negative result
meaningful.

Adding `keyval.Models()` and removing `OAuthRequest` from
`oauthserver.Models()` means one generated migration creates `key_values` and
drops `o_auth_requests`.

`internal/db/testutil.NewDB` creates tables from `Models()` via `AutoMigrate`,
so the trigger is absent in SQLite-only unit tests. Consumer tests that build
stores directly must add `keyval.Models()` to their `NewDB` model sets, since
`oauthserver.Models()` no longer carries the table. The Postgres path is
covered separately (below). `sap` and `cmd/home` use `AutoMigrate` and do not
install the trigger; neither is in scope for expiry semantics yet.

### Wiring

`pear` constructs one root store in `cmd/pear/main.go` after
`migrations.Run`, and passes namespaced children to the two consumers. It
replaces `oauthserver.NewCollector`'s role for `o_auth_requests` only;
`o_auth_sessions` still needs `Collector`, which stays.

## Consumers

### `o_auth_requests` → `keyval` namespace `oauth`

The row is already a junk drawer keyed by one opaque string, and already
filtered on expiry at read time, so the shape maps cleanly. What changes is
that the columns become one serialized value.

`fosite.AuthorizeRequest` is **not** serialized directly. It embeds a
`Client` and a `Session` whose unexported state does not survive a JSON
round trip, which is presumably why the existing code flattens to plain
columns via `fromRequester` / `toAuthorizeRequest` in the first place. So the
value is a small purpose-built record with the same exported fields:

```go
type requestRecord struct {
    ClientID             string
    Subject              string
    Scopes               string
    CodeChallenge        string
    CodeChallengeMethod  string
    RedirectURI          string
    State                string
    ResponseType         string
    ResponseMode         string
}
```

`ExpiresAt` leaves the value and becomes the `Put` TTL, and `Key` becomes the
key. `fromRequester` and `toAuthorizeRequest` keep their current shape, so the
diff stays small and the existing fosite plumbing is untouched.

TTLs are unchanged: `parSessionTTL` (10 minutes) for PAR and in-flight
requests, `request.GetExpiresAt(fosite.AuthorizeCode)` for authorization
codes. `UpdatePARSessionSubject` becomes a read-modify-`Put`.

**No data migration.** Every row in `o_auth_requests` expires within minutes
by construction, so existing rows are simply abandoned and the generated
migration drops the table.

**Deploy note:** dropping `o_auth_requests` invalidates in-flight OAuth
authorizations that straddle the deploy — at most one 10-minute window, and
only for users mid-authorize. Acceptable, but it belongs in the release notes.

### Login provider state → `keyval` namespace `login`

Today `login.Provider.Authorize` returns an opaque `providerState []byte` that
`oauthserver` serializes into the signed session cookie, both directly and in
the `login_hops` map keyed by OAuth `state` (so nested sign-ins do not
overwrite each other). For the PDS provider that blob contains a **DPoP
private key** (`internal/login/pds.go:29`), and `sessions.NewCookieStore`
signs but does not encrypt — so it is already crossing the network in
plaintext. Moving it server-side is a security improvement, not a regression.

The provider keeps ownership: it is given the namespaced store at construction
and persists its own state shape. It takes the full `keyval.Store` rather than
the narrower `KV`, because `Authorize` needs `Put` and `Exchange` needs
`Consume`.

```go
func NewGoogleProvider(..., kv keyval.Store) (Provider, error)
func NewPDSProvider(..., kv keyval.Store) Provider
```

The `Provider` interface keeps its three-value `Authorize` return; the third
becomes an opaque **key** instead of the payload:

```go
Authorize(ctx, loginHint) (redirectURI, state, providerStateKey string, err error)
Exchange(ctx, query, providerStateKey string) (loginID string, profile Profile, err error)
```

`Authorize` mints a random key, `Put`s its state under it, and returns the
key; `Exchange` `Consume`s by that key. The password provider, which has no
state, returns empty strings and ignores the key on `Exchange`.

**The cookie still carries the key, and this is deliberate.** Keying the row by
the echoed OAuth `state` would be simpler — the cookie would only need the
request key — but OAuth `state` travels in redirect URLs, so anyone who
observes one could redeem the blob without the session cookie. Keeping a fresh
random key in the signed cookie preserves the existing binding exactly: the
row is reachable only through the cookie that references it. `loginHop` keeps
its shape with `ProviderState` becoming that key, so `saveLoginHop` /
`restoreLoginHop` change only in what fills the field.

TTL is the OAuth session cookie's `MaxAge` (10 minutes, `oauth_server.go:227`),
so a stored entry never outlives the cookie that can reference it.

## Error handling

- `ErrNotFound` is returned for both missing and expired entries, and for
  `Delete` of a key that is not present. One sentinel, because callers cannot
  act differently on the two cases.
- GORM errors are wrapped with `fmt.Errorf` and the operation, matching the
  surrounding stores.
- Marshalling failures are returned before any database work happens.
- `New` returns an error if table setup or the SQLite startup sweep fails.
  Failing to build the store is fatal at boot, not a degraded mode: silently
  running without it would turn every `Put` into a runtime error later.

## Testing

`internal/keyval/keyvaltest` provides a Postgres testcontainer, mirroring
`internal/search/searchtest`: a `HABITAT_TEST_PGURL` env override, otherwise a
`postgres:16-alpine` container. The same table-driven tests run against it and
against the existing SQLite harness from `internal/db/testutil`.

This split is deliberate. `internal/db/testutil.NewDB` is SQLite-only, and
Postgres appears in unit tests only in `cmd/pear/pear_test.go`; without this
helper the trigger would ship untested. `keyvaltest` needs a
`.testcoverage.yml` exclusion, matching the `internal/search/searchtest` line.

Covered: put/get round trip; JSON shape errors; upsert overwrites value and
expiry; namespace isolation in both directions (a namespaced store cannot read,
overwrite or delete another namespace, and cannot be tricked by a foreign key);
TTL expiry reading as missing; `Delete`; `Consume` returning the value and
removing it; concurrent `Consume` on one key yielding exactly one success;
SQLite startup sweep deleting only expired rows; Postgres trigger sweeping
expired rows on a subsequent write and leaving unexpired rows alone.

Consumer tests are updated rather than added: `internal/login`'s existing
tests for the new signatures, and `internal/oauthserver`'s storage and MCP
tests for the blob-backed store. `cmd/pear/pear_test.go` already boots pear
against both a SQLite file and a Postgres container, so it exercises trigger
installation at startup end to end.

## Risks

- **Idle tables do not shrink on Postgres.** Accepted. Reads are unaffected; the
  cost is disk. Fixable later with the existing `Collector` pattern.
- **Sustained write load can starve the sweep.** Accepted; the advisory lock is
  the throttle, and skipping a sweep only defers it.
- **Dropping `o_auth_requests` breaks in-flight authorizations across a
  deploy**, bounded by the 10-minute TTL. Accepted, noted for release notes.
- **JSON round-trip fidelity** is the main correctness risk in the
  `o_auth_requests` migration, since fosite types do not round-trip. Keeping
  the explicit `requestRecord` rather than serializing `AuthorizeRequest`
  directly is what bounds it.
