# Working with spaces

The [permissioned data proposal](https://github.com/bluesky-social/proposals/blob/main/0016-permissioned-data/README.md) is the real description of the data model and is worth reading in full. This page is the short version of it, plus the parts that are specific to working through Habitat.

## What a space is

A space is a boundary around a set of records. Everything inside it is permissioned: records in a space never land in the user's public repo and never show up on the firehose. Getting at them means being granted access to the space.

A space is identified by an `(authority, type, skey)` triple, written as a URI:

```
ats://did:web:pear.habitat.network/network.habitat.group/3lartabcd2s22
      └─────── authority ────────┘ └────── type ───────┘ └── skey ───┘
```

- **authority** — the DID that owns the space and issues credentials for it. On Habitat this is always Habitat's own DID rather than the creating user's; see [Simple Spaces](./overview.mdx).
- **type** — an NSID for the kind of space this is: a group, a user's personal data, gated content. Apps use it to recognize spaces they know how to render, and `listSpaces` filters on it.
- **skey** — a record key that distinguishes spaces of the same type under the same authority. Auto-generated as a TID if you don't pass one.

## A space is a union of repos

A space is not one shared document. Every member gets their **own permissioned repo** scoped to that space, and the space is the union of those repos. Record URIs extend the space URI with the repo that holds the record:

```
ats://did:web:pear.habitat.network/network.habitat.group/3lartabcd2s22/did:plc:alice/community.lexicon.calendar.event/3lb4kq7xk2s2s
└────────────────────────────── space ───────────────────────────────┘ └── repo ───┘ └───────── collection ─────────┘ └── rkey ───┘
```

You can only ever write to your own repo, so there are no write conflicts to resolve — Alice can't edit Bob's copy of a record, she writes her own and readers reconcile the two. It also means each repo is signed and synced independently, which is what the per-repo commits and op logs in the sync endpoints are for.

## Spaces as permission boundaries

**Permissions attach to the space, not to records or collections.** There is no per-record ACL and no per-collection grant: if you can read a space, you can read every record in every member's repo in it. Widening access to something means adding a member to the space that holds it; narrowing it means putting the data in a different space. Deciding how to slice your data into spaces _is_ the access-control design.

Habitat stores these grants in a relationship store rather than as a member list hanging off the space, so a grant is a relation between a user and the space:

| Relation             | Who has it                            | What it allows                                                        |
| -------------------- | ------------------------------------- | --------------------------------------------------------------------- |
| `owner`              | the creator, and the authority itself | everything below, plus `deleteSpace`                                  |
| `can_manage_members` | owners                                | `addMember` and `removeMember`                                        |
| `can_write`          | anyone added with `addMember`         | write records to their own repo, plus everything `can_read` allows    |
| `can_read`           | implied by `can_write`                | read every repo in the space, list its members and repos, and sync it |

Every space endpoint resolves the caller to a DID and checks the relevant relation against the space before it does anything else. A caller who fails the check gets `SpaceNotFound` rather than a permission error, so a space's existence isn't leaked to people outside it.

Because grants are relations and not a flat list, the underlying model can also grant a role on one space to the members of another — groups as grantees, nested groups. `simplespace.addMember` only takes a single DID today, but the store behind it is built for that.

## Working in a space

The examples below assume `$TOKEN` is an access token from the [OAuth flow](./getting-started.mdx#authentication).

Create a space. The authority is assigned by Habitat, so omit `did`:

```bash
curl -X POST https://pear.habitat.network/xrpc/network.habitat.simplespace.createSpace \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"type": "network.habitat.group"}'
# {"uri": "ats://did:web:pear.habitat.network/network.habitat.group/3lartabcd2s22"}
```

Add a member, which grants them write access to their own repo in the space and read access to everyone else's. Only someone who can manage members — the creator, in practice — can do this:

```bash
curl -X POST https://pear.habitat.network/xrpc/network.habitat.simplespace.addMember \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"space": "'$SPACE'", "did": "did:plc:bob"}'
```

Write a record. `repo` has to be the authenticated caller's own DID:

```bash
curl -X POST https://pear.habitat.network/xrpc/network.habitat.space.putRecord \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
        "space": "'$SPACE'",
        "repo": "'$MY_DID'",
        "collection": "community.lexicon.calendar.event",
        "record": {"name": "Standup"}
      }'
# {"uri": "ats://.../3lart.../did:plc:alice/community.lexicon.calendar.event/3lb...", "cid": "bafy..."}
```

Read a member's records. Any member of the space can read any other member's repo:

```bash
curl -G https://pear.habitat.network/xrpc/network.habitat.space.listRecords \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "space=$SPACE" --data-urlencode "repo=did:plc:alice"
```

`network.habitat.space.deleteRecord` removes a record, and `network.habitat.repo.uploadBlob` / `network.habitat.space.getBlob` handle binary attachments.

## Syncing a space

Syncing is per repo. A syncer walks the writer set, then pulls each repo's ops since the revision it last saw:

- `network.habitat.space.listSpaces` — the spaces the caller can read, optionally filtered by `type` or owner `did`.
- `network.habitat.space.listRepos` — the writer set, with each repo's current rev and commit hash.
- `network.habitat.space.listRepoOps` — a repo's ops after a given rev, for incremental sync. The last page includes the current signed commit.
- `network.habitat.space.getLatestCommit` / `getRepo` — the signed head, and full state as a CAR file for recovery.

A service syncing on a user's behalf doesn't use their OAuth token: it exchanges a delegation token for a space credential good for the whole space. How Habitat signs both, and how a verifier tells a Habitat-signed commit from a spec one, is covered under [Signing](./overview.mdx).

[Endpoints](./endpoints.mdx) lists every method with its status, and the [HTTP reference](/docs/api/habitat-api) has the request and response schemas.
