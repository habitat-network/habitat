# simplespace compatibility

Applications that are only compatible with simplespaces will still work with ReBAC spaces.
The `network.habitat.simplespace.*` methods are a narrow view onto the same relation graph the `network.habitat.relationship.*` methods write to.

## How the methods map

| Simplespace method | What it does in the graph                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------- |
| `createSpace`      | Grants the creator [`owner`](./overview.mdx#roles) on the new space, as a [`userRelation`](./records.mdx#userrelation) record. |
| `addMember`        | Grants the new member `writer` |
| `removeMember`     | Revokes the DID's grant on the space, whichever role it was.                                               |
| `listMembers`      | The **expanded** set of DIDs holding `reader`, identical to [`resolveRelations`](./endpoints.mdx#listing) with `relation: reader`. |
| `deleteSpace`      | Deletes the space and every relation governing it.                                                         |

Two consequences fall out of the [role implication chain](./overview.mdx#roles):

- **A "member" is anyone with `reader`.** Since `owner ⇒ manager ⇒ writer ⇒ reader`, everyone the graph grants any role to is a member as far as simplespace is concerned. `addMember` grants `writer` because that is what a plain simplespace member is expected to be able to do — write into the space.
- **The space owner is a member without a record.** The DID in the space URI holds `owner` implicitly, which is why `removeMember` refuses to remove it.

## Where the two views diverge

Simplespace's vocabulary is smaller than the graph's, so reading a ReBAC space through it is lossy in three specific ways.

**`listMembers` flattens.** It returns DIDs, so a member who is only there because their group was granted a role appears as a bare DID, indistinguishable from a direct grant — and their role is not reported at all. Use [`listRelations`](./endpoints.mdx#listing) to see the structure that produced that list.

**`removeMember` only removes direct grants.** It deletes the user's `userRelation` on that space. If the user also reaches the space through a `spaceRelation` — say they are a reader of a group that is a writer here — they remain a member afterward, and `listMembers` will still return them. Removing them for real means removing them from the group, or removing the group's grant with [`deleteRelation`](./endpoints.mdx#writing-relations).

**`addMember` cannot express anything but `writer`.** Granting a reader-only member, a manager, or a userset requires the relationship methods.

None of these are states a simplespace client can create on its own — a space only ever managed through `addMember`/`removeMember` holds nothing but direct user grants, and the two views stay exactly in step. The divergence only shows up once some other app uses the relationship methods to update the ACL.
